## 模块划分

本阶段使用固定的 LLM、TTS、角色和音色配置，统一由后端读取 `.env` 或配置文件。先完成：创建项目 → 提交原文 → 生成脚本 → 确认脚本 → 生成完整音频 → 播放下载。

- **用户模块：**实现用户的登录注册登出等功能，以及接口的鉴权。
- **项目模块**：输入项目标题创建项目；保存用户确认提交的原文（提交成功后就不再允许用户修改原文），通过上传txt保存原文；查询项目列表，查询项目详情。
- **脚本模块**：用户点击生成脚本后，后台调用 LLM 生成结构化脚本；保存有序脚本句（包括台词角色等信息），供用户查看并确认；用户可以修改某条脚本句的内容（台词，角色，语速等等），点击保存修改会重新提交脚本；点击确认脚本将会修改脚本状态为已确认（同一时间只能有一版脚本处于确认状态，如果想确认另一版本的脚本，必须取消确认；已确认的脚本不能再修改内容）。
- **语音模块**：读取已确认的脚本的前三条脚本句生成试听；完整生成：读取已确认脚本，后台逐句合成并返回给前端让用户检查逐句试听，同时生成完整版MP3；保留用户逐句修改的接口，点击重新生成某句后 ，后台会重新生成指定的语句；提供完整MP3音频的下载接口。
- **任务模块**：统一保存脚本和音频任务状态、结果及错误，供前端轮询。
- **配置模块：**主要包括LLM配置和音频生成配置；用户可以选择一种LLM模型作为脚本生成模型，同时用户也可以添加自己的API密钥来调用自己的LLM；用户可以添加角色，并修改角色配置。

**补充说明：**

1. 脚本版本问题：如果用户点击了重新生成脚本，就在数据库中添加一个新的版本的脚本，而如果用户只是手动修改了脚本内容，直接去数据库中修改脚本句的信息，不修改版本。
2. 音频版本问题：音频任务分为试听生成，完整生成和重新生成三种。只有完整生成会生成新的版本，并且需要附带脚本快照；重新生成后，会让用户决定保留哪一版，然后直接在数据库中覆盖。
3. 通过外键将用户、项目、脚本、音频联系起来，用户可以查询到自己的所有项目，以及每个项目对应的原文、各版本脚本以及各版本音频（前端最好可以展示每次生成的各版本脚本）。原文不需要版本，如果用户修改了原文直接在数据库中更改。
4. 音频重新生成功能：现阶段我们只使用了简单粗暴的重新生成的解决方式，后期考虑改进重新生成方式，如用户可以输入自然语言让LLM调整脚本内容后再重新生成语句，或给出一些选项如“太平淡”“语速太快”“停顿不自然”“读音不对”等让后台处理后再重新生成。
5. 暂时没有预留声音克隆的接口。等主要功能实现后再添加。

**第一阶段最小闭环：**

1. 创建项目，提交原文，确认原文；
2. 生成脚本，确认脚本；
3. 生成音频，音频下载；

## 现阶段任务

### 音频生成

本阶段负责接入一套固定的 TTS 服务，完成从已确认脚本 → 按角色逐句合成 → 合并完整 MP3的流程。

**实现入口与调用位置**

- 现有模拟方法：[mock.py 中的 `MockAudioGenerator.generate(self, snapshot)`](D:/Main/Programs/ZhuoGong/backend/app/integrations/mock.py:32)。当前先 `time.sleep(10)`，再读取固定测试 MP3，需要将这部分替换成真实 TTS 逻辑。
- 调用位置：[worker.py 的 `Worker.run_once()`](D:/Main/Programs/ZhuoGong/backend/app/worker.py:46)，执行 `self.audio_generator.generate(deepcopy(job["snapshot"]))`。
- 也可新建生成服务类，实现相同的 `generate(snapshot)` 方法，再在 `Worker.__init__()` 中替换 `MockAudioGenerator()`。协议和返回类型定义见 [contracts.py](D:/Main/Programs/ZhuoGong/backend/app/integrations/contracts.py)。

**输入参数**

`snapshot` 是任务提交时由后端组装并保存到 `tasks.input_snapshot` 的字典，不是前端直接提交的请求体。Worker 读取快照后传入方法，成员无需重新查询数据库。

| 字段 | 内容及使用方式 |
| --- | --- |
| `source_text`、`source_hash` | 原文及哈希，音频合成主要使用下面的脚本 |
| `simulated` | 当前框架固定为 `True`；接入真实服务时需同步调整该模拟标识 |
| `script` | 已确认脚本的完整快照，含脚本 ID、版本、编辑修订号、标题、状态等 |
| `script.roles` | 脚本角色列表，包含 `role_id`、名称及 `voice_config` 声音配置 |
| `script.sentences` | 有序脚本句列表，每句包含 `sentence_id`、`sequence`、`role_id`、`text`、`speed`、`extra_params` |

按 `sequence` 顺序处理台词，通过句子的 `role_id` 匹配 `script.roles` 中的声音配置。`speed` 可能为 `None`，`extra_params` 可能为空，应使用固定默认配置。当前角色声音配置也是模拟值，需与框架负责人对齐真实 TTS 所需字段并更新固定配置。

**返回结果与职责边界**

返回 `GeneratedAudio(content=..., duration_ms=..., metadata=...)`：

| 字段 | 类型 | 要求 |
| --- | --- | --- |
| `content` | `bytes` | 合并后的完整 MP3 文件字节，不是文件路径或 URL |
| `duration_ms` | `int` | 实际音频时长，单位毫秒，必须大于 0 |
| `metadata` | `dict` | 可 JSON 序列化的元数据，如采样率、声道、服务与模型标识；真实生成时移除测试音说明并正确设置模拟标识 |

生成方法负责调用 TTS、处理片段和合并音频，不直接维护数据库版本、保存最终资源记录或修改任务状态。返回后，由 `publish_audio()` 统一保存 MP3、资源和音频版本结果，并将任务标记成功；失败时抛出异常交给 Worker 处理，不返回测试文件冒充成功。

**联调方式**

使用 `POST /api/v1/projects/{project_id}/audio/generate` 提交已确认脚本，携带 `Idempotency-Key`，请求体为 `script_id`、`expected_script_version`、`expected_edit_revision`。通过 `GET /api/v1/tasks/{task_id}` 查询任务，成功后使用结果中的 `play_url` / `download_url` 检查音频。当前接口只发布完整 MP3，逐句音频的持久化及对外查询需要后续另行补充。

### 脚本生成

本阶段负责接入一套固定的 LLM，将用户原文转换成符合约定的结构化播客脚本。先完成稳定生成、格式校验和角色分配，不要求实现多厂商切换及用户自带密钥。以下说明以当前后端代码为准。

**实现入口与调用位置**

- 现有模拟方法：[mock.py 中的 `MockScriptGenerator.generate(self, snapshot)`](D:/Main/Programs/ZhuoGong/backend/app/integrations/mock.py:15)。当前先 `time.sleep(10)`，再读取固定测试脚本，需要将这部分替换成真实 LLM 调用。
- 调用位置：[worker.py 的 `Worker.run_once()`](D:/Main/Programs/ZhuoGong/backend/app/worker.py:43)，执行 `self.script_generator.generate(deepcopy(job["snapshot"]))`。
- 也可新建生成服务类，实现相同的 `generate(snapshot)` 方法，再在 `Worker.__init__()` 中替换 `MockScriptGenerator()`。协议和返回类型同样定义在 `contracts.py` 中。

**输入参数**

`snapshot` 是任务提交时保存的字典，由后端查询原文、模型和角色配置后组装，Worker 将其副本传给生成方法。组装逻辑见 [repository.py 的 `submit()`](D:/Main/Programs/ZhuoGong/backend/app/jobs/repository.py:31)。

| 字段 | 内容及使用方式 |
| --- | --- |
| `source_text` | 用户提交的完整原文，作为脚本生成的主要输入 |
| `source_hash` | 原文哈希，用于追溯输入 |
| `simulated` | 当前框架固定为 `True`；接入真实服务时需同步调整该模拟标识 |
| `model` | `model_id`、`provider_code`、`model_code`、`params`；当前是模拟配置，接入时需要更新为实际固定配置 |
| `prompt` | 当前为模拟提示词，需要替换为真实提示词模板，建议在提交任务时固定并保存到快照 |
| `roles` | 用户选择的角色，每项含 `profile_id`、`role_key`、`name`、`description`、`voice_config`；生成台词使用对应的 `role_key` |

真实服务需要的 API 密钥由服务端环境配置读取，不写入任务快照或返回结果。

**返回结果与职责边界**

返回 `GeneratedScript` 对象，可用 `GeneratedScript.model_validate(解析后的字典)` 校验模型输出。结构示例：

```json
{
  "title": "本期播客标题",
  "summary": "本期内容简介",
  "sentences": [
    {"role_key": "host", "text": "大家好，欢迎收听本期播客。"},
    {"role_key": "host", "text": "今天我们来讨论原文中的主要内容。"}
  ]
}
```

上例假定输入角色包含 `role_key: "host"`。实际必须使用输入角色的标识，不能由 LLM 随意创建新角色。句子数组的顺序就是播放顺序，句子 ID、角色数据库 ID、顺序号和脚本版本由框架生成，不需要模型输出。

当前校验要求：标题 1～100 字符、`summary` 为字符串、至少一条台词、每句 1～1000 字符且不能全为空白、台词总长度不超过 5000 字符；所有输入角色都要有台词，输出不得包含协议之外的额外字段。若需要生成更长脚本，先与框架负责人统一调整限制。

生成方法负责提示词构造、模型调用、响应解析和必要的格式修复；不要直接写脚本表或修改任务状态。返回后，由 `publish_script()` 统一创建脚本新版本、角色和有序脚本句，并完成任务。调用或解析失败时抛出异常，交给 Worker 记录失败。

**联调方式**

使用 `POST /api/v1/projects/{project_id}/script/generate` 提交角色数组，携带 `Idempotency-Key`；通过 `GET /api/v1/tasks/{task_id}` 取得成功结果中的 `script_id`，再通过 `GET /api/v1/scripts/{script_id}` 查看脚本。确认接口是当前实现的 `POST /api/v1/scripts/{script_id}/confirm`，请求体包含 `expected_script_version` 和 `expected_edit_revision`。

两名成员均不需要另建任务队列或在 API 内启动生成线程。长耗时方法由独立 Worker 执行；接入后重启 Worker，使新代码和配置生效。
