- 脚本任务 1 使用 `verbatim` 模式，12:52:09 已成功完成，没有调用 LLM 改写。
- 音频任务 2 于 12:53:12 开始，13:09:56 成功完成，约耗时 16 分 44 秒，完成 37 / 37 句。
- Worker 日志记录 `Task completed: id=2 type=audio`；数据库任务状态为 `succeeded`，音频版本为 `ready`。
- 输出 MP3 为 7,210,413 字节；ffprobe 检查时长为 450.648 秒（约 7 分 31 秒）。

根因是前端 `pollTask` 默认等待上限只有 10 分钟，抛出普通 Error 后，音频生成面板将其替换为“生成失败”。前端停止等待不会取消 Worker，导致页面提示与实际状态不一致。该原文未超出输入长度限制，日志未显示这次任务发生模型错误。

修复：

1. 默认轮询等待后端终态，不以等待 10 分钟作为生成失败判据；显式配置等待上限时，提示后台可能仍在运行。
2. 提交后立即显示已创建的音频版本；版本页每 2 秒刷新，刷新页面也能恢复查看后台任务，避免重复提交。
3. Worker 记录每个语音分片的开始、完成、耗时和总分片数；持久化进度及完成句数，前端显示累计完成句数。
4. 编码合并单独记录阶段；版本页刷新不再反复切换成加载骨架。
5. 控制台对子进程强制 `PYTHONUNBUFFERED=1`，避免普通 Python print 被文件缓冲；页面显示最近日志读取时间。

控制台原有日志就是轮询更新：每轮完成后约 1.2 秒再刷新一次，每次读取所选服务/任务日志末尾 64 KB，不是 SSE/WebSocket 推送。刷新周期还受请求耗时和浏览器后台节流影响。旧 Worker 仅记录任务启动/最终结果，TTS 的 HTTP 访问日志通常等一个分片请求完成后才写入，因此长时间看起来没有新输出。

验证包括前端超过 10 分钟仍等待的回归测试、后端分片进度与 API 完成句数测试、子进程未退出即可读取日志的控制台测试，以及本次真实音频文件检查。回归测试不会再次运行这篇原文的完整语音合成。
