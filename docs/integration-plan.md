# TextCast 集成计划

## 目标架构

浏览器只负责输入、审核和状态展示。后端负责重复校验、持久化、调用 LLM/TTS、保存任务快照与音频文件，并只允许下载本系统生成的文件。

正式流程分成两个独立的异步阶段：

```text
原文 -> 脚本生成任务 -> 可编辑脚本版本 -> 用户确认
     -> 音频生成任务 -> 可播放音频版本 -> 下载
```

脚本生成成功不等于音频生成成功；音频失败重试不得自动重跑 LLM。每次音频任务必须保存 `scriptVersionId` 与声音参数快照，以便验收时证明“听到的内容来自哪一版确认脚本”。

## 当前两套接口的关系

| 范围 | 前端已有契约 | Python 原型 | 处理方式 |
| --- | --- | --- | --- |
| 项目 | `/api/projects` | 无 | 正式后端新增，不修改前端去适配原型。 |
| 脚本版本 | `/api/projects/:id/scripts`、`/api/scripts/:id` | 无 | 增加脚本任务后，由正式后端持久化。 |
| 脚本生成任务 | 尚未完整定义 | 无 | 优先冻结契约，状态沿用统一任务枚举。 |
| 试听/全文生成 | `/api/generation/preview`、`/api/generation/full` | `/api/jobs` | 正式后端采用前端语义；可复用原型任务实现思路。 |
| 任务查询 | `/api/generation/tasks/:id` | `/api/jobs/:id` | 统一为带 `stage` 的任务响应。 |
| 音频 | 音频版本 URL | `/api/jobs/:id/audio` | 正式后端返回受控下载 URL 和文件名。 |

`backend/prototype` 保持为可运行样例，不再扩展成第二套生产接口。正式接口落地后，MSW handler、TypeScript 类型和后端 DTO 必须在同一个 Pull Request 中同步。

## 建议的统一任务字段

```json
{
  "id": "task-id",
  "stage": "script",
  "status": "queued",
  "projectId": "project-id",
  "inputSnapshot": {},
  "result": null,
  "error": null,
  "createdAt": "2026-10-17T00:00:00Z",
  "updatedAt": "2026-10-17T00:00:00Z"
}
```

- `stage`：`script` 或 `audio`。
- `status`：`queued`、`running`、`succeeded`、`failed`。
- `inputSnapshot`：不可变的原文/脚本版本和参数快照。
- `error`：至少包含稳定错误码、用户可理解消息和可选调试详情。

## 分阶段交付

### 第一阶段：接口与数据基线

- 根据需求固定 100 KB TXT 建议上限、5000 字建议上限及 UTF-8 行为。
- 定义数据库实体：项目、原文、脚本版本、任务、音频版本。
- 定义统一错误格式、时间格式、跨域和开发环境变量。
- 增加接口契约测试，确保 Mock 与正式后端响应一致。

### 第二阶段：脚本闭环

- 原文创建和更新由真实 API 持久化。
- LLM 调用在后端异步执行，前端只轮询任务状态。
- 用户可以编辑脚本并创建版本；只有明确确认的版本可进入音频阶段。
- 覆盖空输入、超长、服务失败、重试和修改后重新确认。

### 第三阶段：音频闭环

- TTS 根据确认脚本、性别、风格和语速创建任务。
- 支持短文试听与全文生成，记录服务端状态和失败原因。
- 验证长文分段、顺序合并、末尾完整性和中文/数字/英文朗读。
- 播放与下载由后端检查文件归属和存在性，不接受任意磁盘路径。

### 第四阶段：验收与部署

- 增加单元、接口及端到端测试，并在 CI 中运行。
- 在一台未参与开发的电脑上按 README 全新安装和启动。
- 记录 LLM/TTS 服务、模型、参数、耗时、费用和失败恢复策略。
- 清理演示入口、无实现按钮、示例账号和不存在的音频链接。

## 合并门槛

每个功能 Pull Request 至少提供：需求编号、接口样例、自动化测试或可复现人工步骤、成功/失败截图，以及对密钥、用户输入和文件下载的安全说明。前端不得只修改本地 Query 缓存来冒充服务端保存成功。
